## この認定について

Claude Certified Architect – Foundations 認定は、Claudeを用いた実世界のソリューション実装においてトレードオフに関する十分な情報に基づいた意思決定ができることを検証するものです。この試験は、**Claude Code**、**Claude Agent SDK**、**Claude API**、**Model Context Protocol（MCP）**——Claudeを用いたプロダクショングレードのアプリケーションを構築するための中核技術——にわたる基礎知識を測定します。

本試験の問題は、実際の顧客のユースケースから引用された現実的なシナリオに基づいています。カスタマーサポート向けエージェント型システムの構築、マルチエージェントリサーチパイプラインの設計、Claude CodeのCI/CDワークフローへの統合、開発者生産性ツールの構築、非構造化ドキュメントからの構造化データ抽出などが含まれます。受験者は概念的な知識だけでなく、プロダクション環境におけるアーキテクチャ・設定・トレードオフに関する実践的な判断力を示す必要があります。

本ガイドは、試験の受験を準備する受験者にとっての権威ある参照資料です。試験内容、出題されるドメインとタスクステートメントの一覧、サンプル問題、および推奨される準備戦略を説明しています。試験を予約する前に、本ガイドの全体を読んでください。

## 対象となる受験者

この認定の理想的な受験者は、Claudeを用いてプロダクションアプリケーションを設計・実装するソリューションアーキテクトです。この受験者は以下について実務経験を有しています：

- マルチエージェントオーケストレーション、サブエージェントへの委譲、ツール統合、ライフサイクルフックを含む、Claude Agent SDKを用いたエージェント型アプリケーションの構築
- CLAUDE.mdファイル、Agent Skills、MCPサーバー統合、プランモードを用いたチームワークフロー向けのClaude Codeの設定とカスタマイズ
- バックエンドシステム統合のためのModel Context Protocol（MCP）ツール・リソースインターフェースの設計
- JSONスキーマ、few-shot例、抽出パターンを活用した、信頼性の高い構造化出力を生成するプロンプトのエンジニアリング
- 長いドキュメント、複数ターンの会話、マルチエージェントのハンドオフにわたるコンテキストウィンドウの効果的な管理
- 自動コードレビュー、テスト生成、プルリクエストフィードバックのためのCI/CDパイプラインへのClaude統合
- エラーハンドリング、human-in-the-loopワークフロー、自己評価パターンを含む、健全なエスカレーションおよび信頼性に関する意思決定

受験者は通常、Claude API、Agent SDK、Claude Code、MCPを用いた構築における**6ヶ月以上**の実務経験を持ち、プロダクション環境における大規模言語モデルの能力と限界の両方を理解しています。

## 試験シナリオ

本試験ではシナリオベースの問題を使用します。各シナリオは、一連の問題の枠組みとなる現実的なプロダクション文脈を提示します。試験中には、以下の**6つのシナリオ**全体から無作為に選ばれた**4つのシナリオ**が提示されます。

### シナリオ1: Customer Support Resolution Agent（カスタマーサポート解決エージェント）

あなたはClaude Agent SDKを使ってカスタマーサポート解決エージェントを構築しています。このエージェントは、返品、請求の異議申し立て、アカウントの問題といった曖昧性の高いリクエストを処理します。カスタムのModel Context Protocol（MCP）ツール（`get_customer`、`lookup_order`、`process_refund`、`escalate_to_human`）を通じてバックエンドシステムにアクセスできます。目標は、エスカレーションすべきタイミングを見極めながら、**初回接触解決率80%以上**を達成することです。

**主要ドメイン:** Agentic Architecture & Orchestration、Tool Design & MCP Integration、Context Management & Reliability

### シナリオ2: Code Generation with Claude Code（Claude Codeによるコード生成）

あなたはソフトウェア開発を加速するためにClaude Codeを使用しています。あなたのチームは、コード生成、リファクタリング、デバッグ、ドキュメント作成にこれを使用しています。カスタムスラッシュコマンドとCLAUDE.md設定を用いて開発ワークフローに統合する必要があり、プランモードと直接実行のどちらを使うべきかを理解する必要があります。

**主要ドメイン:** Claude Code Configuration & Workflows、Context Management & Reliability

### シナリオ3: Multi-Agent Research System（マルチエージェントリサーチシステム）

あなたはClaude Agent SDKを使ってマルチエージェントのリサーチシステムを構築しています。コーディネーターエージェントが専門化されたサブエージェントに委譲します：1つはWebを検索し、1つはドキュメントを分析し、1つは調査結果を統合し、1つはレポートを生成します。このシステムはトピックを調査し、引用付きの包括的なレポートを生成します。

**主要ドメイン:** Agentic Architecture & Orchestration、Tool Design & MCP Integration、Context Management & Reliability

### シナリオ4: Developer Productivity with Claude（Claudeによる開発者生産性向上）

あなたはClaude Agent SDKを使って開発者生産性ツールを構築しています。このエージェントは、エンジニアが馴染みのないコードベースを探索し、レガシーシステムを理解し、ボイラープレートコードを生成し、反復作業を自動化するのを支援します。組み込みツール（Read、Write、Bash、Grep、Glob）を使用し、Model Context Protocol（MCP）サーバーと統合します。

**主要ドメイン:** Tool Design & MCP Integration、Claude Code Configuration & Workflows、Agentic Architecture & Orchestration

### シナリオ5: Claude Code for Continuous Integration（継続的インテグレーションのためのClaude Code）

あなたはClaude CodeをContinuous Integration/Continuous Deployment（CI/CD）パイプラインに統合しています。このシステムは自動コードレビューを実行し、テストケースを生成し、プルリクエストへのフィードバックを提供します。実行可能なフィードバックを提供し、誤検知（false positive）を最小化するプロンプトを設計する必要があります。

**主要ドメイン:** Claude Code Configuration & Workflows、Prompt Engineering & Structured Output

### シナリオ6: Structured Data Extraction（構造化データ抽出）

あなたはClaudeを使って構造化データ抽出システムを構築しています。このシステムは非構造化ドキュメントから情報を抽出し、JavaScript Object Notation（JSON）スキーマを用いて出力を検証し、高い精度を維持します。エッジケースを適切に処理し、下流システムと統合できなければなりません。

**主要ドメイン:** Prompt Engineering & Structured Output、Context Management & Reliability

## ドメイン別の詳細な出題目標

以下の各ドメインには、出題されるタスクステートメントと、それぞれに対して測定される知識・スキルが記載されています。試験問題はこれらの目標に基づいて作成されています。

## Domain 1: Agentic Architecture & Orchestration（エージェント型アーキテクチャとオーケストレーション）

### Task Statement 1.1: 自律的なタスク実行のためのエージェント型ループの設計と実装

**知識:**
- エージェント型ループのライフサイクル：Claudeへのリクエスト送信、`stop_reason`（`"tool_use"` vs `"end_turn"`）の確認、要求されたツールの実行、次のイテレーションのための結果の返却
- モデルが次のアクションについて推論できるように、ツールの結果が会話履歴にどのように追加されるか
- モデル駆動の意思決定（Claudeがコンテキストに基づいて次に呼び出すツールを推論する）と、事前設定された決定木やツールシーケンスとの違い

**スキル:**
- `stop_reason`が`"tool_use"`のときに継続し、`"end_turn"`のときに終了する、エージェント型ループの制御フローの実装
- モデルが新しい情報を推論に取り込めるよう、イテレーション間でツールの結果を会話コンテキストに追加すること
- ループ終了を判定するために自然言語のシグナルを解析すること、主要な停止メカニズムとして恣意的なイテレーション上限を設定すること、完了指標としてアシスタントのテキストコンテンツの有無を確認すること、といったアンチパターンの回避

### Task Statement 1.2: コーディネーター・サブエージェントパターンによるマルチエージェントシステムのオーケストレーション

**知識:**
- コーディネーターエージェントがすべてのサブエージェント間通信、エラーハンドリング、情報ルーティングを管理するHub-and-spoke（ハブアンドスポーク）アーキテクチャ
- サブエージェントが隔離されたコンテキストで動作すること——コーディネーターの会話履歴を自動的に継承しないこと
- タスク分解、委譲、結果の集約、クエリの複雑さに応じてどのサブエージェントを呼び出すかの決定における、コーディネーターの役割
- コーディネーターによる過度に狭いタスク分解のリスク——広範なリサーチトピックのカバレッジ不足につながること

**スキル:**
- 常に全体パイプラインを通すのではなく、クエリの要件を分析して動的にどのサブエージェントを呼び出すかを選択するコーディネーターエージェントの設計
- 重複を最小化するためのサブエージェント間でのリサーチ範囲の分割（例：各エージェントに異なるサブトピックやソースの種類を割り当てる）
- コーディネーターが統合出力のギャップを評価し、対象を絞ったクエリで検索・分析サブエージェントに再委譲し、カバレッジが十分になるまで統合を再実行する、反復的な改善ループの実装
- 可観測性、一貫したエラーハンドリング、制御された情報フローのために、すべてのサブエージェント間通信をコーディネーター経由でルーティングすること

### Task Statement 1.3: サブエージェントの呼び出し、コンテキスト受け渡し、スポーンの設定

**知識:**
- サブエージェントをスポーンするメカニズムとしてのTaskツール、およびコーディネーターがサブエージェントを呼び出すために`allowedTools`に`"Task"`を含める必要があるという要件
- サブエージェントのコンテキストはプロンプト内で明示的に提供されなければならないこと——サブエージェントは親のコンテキストを自動的に継承したり、呼び出し間でメモリを共有したりしないこと
- 各サブエージェントタイプの説明、システムプロンプト、ツール制限を含む`AgentDefinition`の設定
- 共有の分析ベースラインから分岐したアプローチを探索するためのフォークベースのセッション管理

**スキル:**
- 先行するエージェントからの完全な調査結果をサブエージェントのプロンプトに直接含めること（例：Web検索結果とドキュメント分析出力を統合サブエージェントに渡す）
- 帰属を保持するためにエージェント間でコンテキストを受け渡す際、構造化されたデータ形式を用いてコンテンツとメタデータ（ソースURL、ドキュメント名、ページ番号）を分離すること
- 個別のターンにまたがるのではなく、単一のコーディネーター応答内で複数のTaskツール呼び出しを発行して並列サブエージェントをスポーンすること
- サブエージェントの適応性を可能にするために、段階的な手続き的指示ではなく、リサーチ目標と品質基準を指定するコーディネーターのプロンプトを設計すること

### Task Statement 1.4: 強制とハンドオフのパターンによる複数ステップのワークフローの実装

**知識:**
- プログラム的な強制（フック、前提条件ゲート）とワークフロー順序に関するプロンプトベースのガイダンスとの違い
- 決定論的な遵守が要求される場合（例：金融操作前の本人確認）、プロンプトの指示だけではゼロではない失敗率が生じること
- 顧客の詳細、根本原因分析、推奨されるアクションを含む、プロセス途中でのエスカレーションのための構造化されたハンドオフプロトコル

**スキル:**
- 前提となるステップが完了するまで下流のツール呼び出しをブロックする、プログラム的な前提条件の実装（例：`get_customer`が検証済みの顧客IDを返すまで`process_refund`をブロックする）
- 複数の懸念事項を含む顧客リクエストを個別の項目に分解し、共有コンテキストを用いて並行して各項目を調査した上で、統一された解決策に統合すること
- 会話のトランスクリプトにアクセスできない人間のエージェントにエスカレーションする際、構造化されたハンドオフサマリー（顧客ID、根本原因、返金額、推奨アクション）を作成すること

### Task Statement 1.5: ツール呼び出しの傍受とデータ正規化のためのAgent SDKフックの適用

**知識:**
- モデルが処理する前に変換するためにツールの結果を傍受する`PostToolUse`などのフックパターン
- コンプライアンスルールを強制するために発信されるツール呼び出しを傍受するフックパターン（例：一定額を超える返金をブロックする）
- 決定論的な保証のためにフックを使用することと、確率的なコンプライアンスのためにプロンプトの指示に依存することとの違い

**スキル:**
- エージェントが処理する前に、異なるMCPツールからの異種混在なデータ形式（Unixタイムスタンプ、ISO 8601、数値のステータスコード）を正規化する`PostToolUse`フックの実装
- ポリシー違反のアクション（例：500ドルを超える返金）をブロックし、代替のワークフロー（例：人間へのエスカレーション）にリダイレクトするツール呼び出し傍受フックの実装
- ビジネスルールが保証されたコンプライアンスを要求する場合に、プロンプトベースの強制よりもフックを選択すること

### Task Statement 1.6: 複雑なワークフローのためのタスク分解戦略の設計

**知識:**
- 固定された順次パイプライン（プロンプトチェーン）を使うべき場合と、中間の調査結果に基づく動的で適応的な分解を使うべき場合
- レビューを順次のステップに分割するプロンプトチェーンのパターン（例：各ファイルを個別に分析し、その後クロスファイルの統合パスを実行する）
- 各ステップで発見された内容に基づいてサブタスクを生成する、適応的な調査計画の価値

**スキル:**
- ワークフローに適したタスク分解パターンの選択：予測可能な多面的レビューにはプロンプトチェーン、オープンエンドな調査タスクには動的分解
- 大規模なコードレビューを、ファイルごとのローカル分析パスと、別途のクロスファイル統合パスに分割し、注意力の希釈を回避すること
- オープンエンドなタスク（例：「レガシーコードベースに包括的なテストを追加する」）を、まず構造をマッピングし、影響の大きい領域を特定し、依存関係が発見されるにつれて適応する優先順位付き計画を作成することで分解すること

### Task Statement 1.7: セッション状態、再開、フォークの管理

**知識:**
- 特定の以前の会話を継続するための、`--resume <session-name>`を用いた名前付きセッションの再開
- 共有の分析ベースラインから分岐したアプローチを探索するための独立したブランチを作成する`fork_session`
- コード修正後にセッションを再開する際、以前に分析したファイルへの変更をエージェントに伝えることの重要性
- 古くなったツール結果とともに再開するよりも、構造化されたサマリーとともに新しいセッションを開始する方が信頼性が高い理由

**スキル:**
- 複数の作業セッションにまたがる名前付きの調査セッションを継続するための、セッション名を用いた`--resume`の使用
- 並行した探索ブランチを作成するための`fork_session`の使用（例：共有されたコードベース分析から2つのテスト戦略やリファクタリングアプローチを比較する）
- セッションの再開（以前のコンテキストがほぼ有効な場合）と、注入されたサマリーとともに新規開始すること（以前のツール結果が古くなっている場合）との使い分け
- 完全な再探索を要求するのではなく、対象を絞った再分析のために、再開されたセッションに特定のファイル変更を伝えること

## Domain 2: Tool Design & MCP Integration（ツール設計とMCP統合）

### Task Statement 2.1: 明確な説明と境界を持つ効果的なツールインターフェースの設計

**知識:**
- LLMがツール選択に用いる主要なメカニズムとしてのツールの説明。最小限の説明は、類似したツール間での信頼性の低い選択につながること
- ツールの説明に入力形式、クエリの例、エッジケース、境界の説明を含めることの重要性
- 曖昧または重複するツールの説明が誤ルーティングを引き起こす方法（例：ほぼ同一の説明を持つ`analyze_content`と`analyze_document`）
- ツール選択に対するシステムプロンプトの表現の影響：キーワードに敏感な指示が意図しないツールの関連付けを生み出す可能性

**スキル:**
- 各ツールの目的、想定される入力・出力、類似の代替ツールに対していつ使うべきかを明確に区別するツールの説明の作成
- 機能的な重複を排除するためのツールの名前変更と説明の更新（例：`analyze_content`をWeb特有の説明を持つ`extract_web_results`に名前変更する）
- 汎用的なツールを、定義された入出力契約を持つ目的特化型のツールに分割すること（例：汎用の`analyze_document`を`extract_data_points`、`summarize_content`、`verify_claim_against_source`に分割する）
- よく書かれたツールの説明を上書きしてしまう可能性のある、キーワードに敏感な指示についてシステムプロンプトを見直すこと

### Task Statement 2.2: MCPツールのための構造化されたエラーレスポンスの実装

**知識:**
- ツールの失敗をエージェントに伝え返すためのMCPの`isError`フラグのパターン
- 一時的なエラー（タイムアウト、サービス利用不可）、検証エラー（無効な入力）、ビジネスエラー（ポリシー違反）、権限エラーの違い
- 均一なエラーレスポンス（一般的な「操作に失敗しました」）が、エージェントが適切な回復判断を下すのを妨げる理由
- 再試行可能なエラーと再試行不可能なエラーの違い、および構造化されたメタデータの返却が無駄な再試行の試みを防ぐ方法

**スキル:**
- `errorCategory`（一時的／検証／権限）、`isRetryable`のブール値、人間が読める説明を含む構造化されたエラーメタデータの返却
- エージェントが適切にコミュニケーションできるよう、ビジネスルール違反に対して`retriable: false`フラグと顧客向けのわかりやすい説明を含めること
- 一時的な障害に対してサブエージェント内でローカルなエラー回復を実装し、ローカルで解決できないエラーのみを部分的な結果と試みた内容とともにコーディネーターに伝播すること
- アクセス失敗（再試行判断が必要）と有効な空の結果（一致なしの成功したクエリを表す）を区別すること

### Task Statement 2.3: エージェント間でのツールの適切な分配とツール選択の設定

**知識:**
- エージェントに過剰な数のツールへのアクセスを与えること（例：4〜5個ではなく18個）が、意思決定の複雑さを増大させることでツール選択の信頼性を低下させるという原則
- 専門分野外のツールを持つエージェントがそれらを誤用する傾向がある理由（例：統合エージェントがWeb検索を試みる）
- スコープを絞ったツールアクセス：エージェントにはその役割に必要なツールのみを与え、特定の高頻度のニーズに対しては限定的なクロスロールツールを与えること
- `tool_choice`の設定オプション：`"auto"`、`"any"`、および強制的なツール選択（`{"type": "tool", "name": "..."}`）

**スキル:**
- 各サブエージェントのツールセットをその役割に関連するものに制限し、専門分野を超えた誤用を防ぐこと
- 汎用的なツールを制約付きの代替ツールに置き換えること（例：`fetch_url`を、ドキュメントURLを検証する`load_document`に置き換える）
- 複雑なケースをコーディネーター経由でルーティングしながら、高頻度のニーズに対してはスコープを絞ったクロスロールツールを提供すること（例：統合エージェント用の`verify_fact`ツール）
- 特定のツールが最初に呼び出されることを保証するために`tool_choice`の強制選択を使用すること（例：エンリッチメントツールの前に`extract_metadata`を強制する）、その後の後続ターンで後続のステップを処理すること
- モデルが会話的なテキストを返すのではなく必ずツールを呼び出すことを保証するために`tool_choice: "any"`を設定すること

### Task Statement 2.4: Claude Codeおよびエージェントワークフローへのmcpサーバーの統合

**知識:**
- MCPサーバーのスコープ：チーム共有ツールのためのプロジェクトレベル（`.mcp.json`）と、個人的・実験的なサーバーのためのユーザーレベル（`~/.claude.json`）
- 認証情報をコミットせずに管理するための、`.mcp.json`内の環境変数展開（例：`${GITHUB_TOKEN}`）
- 設定済みのすべてのMCPサーバーからのツールが接続時に発見され、エージェントに同時に利用可能になること
- 探索的なツール呼び出しを減らすために、コンテンツカタログ（例：課題のサマリー、ドキュメント階層、データベーススキーマ）を公開するメカニズムとしてのMCPリソース

**スキル:**
- 認証トークンのための環境変数展開を伴う、プロジェクトスコープの`.mcp.json`における共有MCPサーバーの設定
- ユーザースコープの`~/.claude.json`における個人的・実験的なMCPサーバーの設定
- エージェントがGrepのような組み込みツールをより高機能なMCPツールよりも優先してしまうのを防ぐために、MCPツールの説明を強化して機能と出力を詳細に説明すること
- 標準的な統合（例：Jira）については既存のコミュニティMCPサーバーをカスタム実装よりも優先し、チーム固有のワークフローのためにカスタムサーバーを取っておくこと
- 探索的なツール呼び出しを必要とせずにエージェントが利用可能なデータを把握できるように、コンテンツカタログをMCPリソースとして公開すること

### Task Statement 2.5: 組み込みツール（Read、Write、Edit、Bash、Grep、Glob）の効果的な選択と適用

**知識:**
- コンテンツ検索のためのGrep（関数名、エラーメッセージ、import文などのパターンについてファイルの内容を検索する）
- ファイルパスのパターンマッチングのためのGlob（名前や拡張子のパターンでファイルを見つける）
- 完全なファイル操作のためのRead/Write、一意なテキストマッチングを用いた対象を絞った修正のためのEdit
- Editが一意でないテキストマッチのために失敗した場合、信頼性の高いファイル修正のフォールバックとしてRead + Writeを使用すること

**スキル:**
- コードベース全体でコードの内容を検索するためのGrepの選択（例：ある関数のすべての呼び出し元を見つける、エラーメッセージを特定する）
- 命名パターンに一致するファイルを見つけるためのGlobの選択（例：`**/*.test.tsx`）
- Editが一意なアンカーテキストを見つけられない場合に、Readでファイル全体を読み込んでからWriteを使用すること
- すべてのファイルを事前に読み込むのではなく、まずGrepでエントリーポイントを見つけ、次にReadでimportをたどりフローをトレースすることで、段階的にコードベースの理解を構築すること
- まずすべてのエクスポートされた名前を特定し、次にコードベース全体で各名前を検索することで、ラッパーモジュールをまたいだ関数の使用箇所をトレースすること

## Domain 3: Claude Code Configuration & Workflows（Claude Codeの設定とワークフロー）

### Task Statement 3.1: 適切な階層・スコープ・モジュール構成を持つCLAUDE.mdファイルの設定

**知識:**
- CLAUDE.md設定の階層：ユーザーレベル（`~/.claude/CLAUDE.md`）、プロジェクトレベル（`.claude/CLAUDE.md`またはルートの`CLAUDE.md`）、ディレクトリレベル（サブディレクトリの`CLAUDE.md`ファイル）
- ユーザーレベルの設定はそのユーザーにのみ適用されること——`~/.claude/CLAUDE.md`内の指示はバージョン管理を通じてチームメイトと共有されないこと
- CLAUDE.mdをモジュール化して保つために外部ファイルを参照するための`@import`構文（例：各パッケージに関連する特定の標準ファイルをインポートする）
- モノリシックなCLAUDE.mdの代替として、トピック固有のルールファイルを整理するための`.claude/rules/`ディレクトリ

**スキル:**
- 設定階層の問題の診断（例：新しいチームメンバーが、指示がプロジェクトレベルではなくユーザーレベルの設定にあるために指示を受け取れない場合）
- メンテナーのドメイン知識に基づいて、各パッケージのCLAUDE.mdに関連する標準ファイルを選択的に含めるための`@import`の使用
- 大きなCLAUDE.mdファイルを、`.claude/rules/`内の焦点を絞ったトピック固有のファイルに分割すること（例：`testing.md`、`api-conventions.md`、`deployment.md`）
- どのメモリファイルが読み込まれているかを確認し、セッションをまたいだ一貫性のない挙動を診断するための`/memory`コマンドの使用

### Task Statement 3.2: カスタムスラッシュコマンドとスキルの作成・設定

**知識:**
- `.claude/commands/`内のプロジェクトスコープのコマンド（バージョン管理を通じて共有される）と、`~/.claude/commands/`内のユーザースコープのコマンド（個人用）の違い
- `context: fork`、`allowed-tools`、`argument-hint`を含むフロントマター設定をサポートするSKILL.mdファイルを持つ、`.claude/skills/`内のスキル
- 分離されたサブエージェントコンテキストでスキルを実行し、スキルの出力がメインの会話を汚染するのを防ぐ、`context: fork`フロントマターオプション
- 個人によるスキルのカスタマイズ：チームメイトに影響を与えないよう、異なる名前で`~/.claude/skills/`に個人用のバリアントを作成すること

**スキル:**
- バージョン管理を通じたチーム全体での利用のために、`.claude/commands/`にプロジェクトスコープのスラッシュコマンドを作成すること
- 冗長な出力を生成するスキル（例：コードベース分析）や探索的なコンテキスト（例：代替案のブレインストーミング）をメインセッションから分離するために`context: fork`を使用すること
- スキル実行中のツールアクセスを制限するために、スキルのフロントマターで`allowed-tools`を設定すること（例：破壊的なアクションを防ぐためにファイル書き込み操作に限定する）
- 開発者が引数なしでスキルを呼び出した際に必要なパラメータを促すための`argument-hint`フロントマターの使用
- スキル（タスク固有のワークフローのためのオンデマンドの呼び出し）とCLAUDE.md（常に読み込まれる普遍的な標準）の使い分け

### Task Statement 3.3: 条件付きの規約読み込みのためのパス固有ルールの適用

**知識:**
- 条件付きルール有効化のためのglobパターンを含むYAMLフロントマターの`paths`フィールドを持つ、`.claude/rules/`ファイル
- パススコープのルールが、一致するファイルを編集する際にのみ読み込まれ、無関係なコンテキストとトークン使用量を削減する方法
- 複数のディレクトリにまたがる規約（例：コードベース全体に分散したテストファイル）に対する、ディレクトリレベルのCLAUDE.mdファイルに対するglobパターンルールの優位性

**スキル:**
- 一致するファイルを編集するときにのみルールが読み込まれるように、YAMLフロントマターによるパススコープ（例：`paths: ["terraform/**/*"]`）を持つ`.claude/rules/`ファイルの作成
- ディレクトリの場所に関わらずファイルの種類ごとに規約を適用するためのパス固有ルールでのglobパターンの使用（例：すべてのテストファイルに対する`**/*.test.tsx`）
- コードベース全体に分散したファイルに規約を適用しなければならない場合に、サブディレクトリのCLAUDE.mdファイルよりもパス固有ルールを選択すること

### Task Statement 3.4: プランモードと直接実行のどちらを使うべきかの判断

**知識:**
- プランモードは、大規模な変更、複数の有効なアプローチ、アーキテクチャ上の決定、複数ファイルの修正を伴う複雑なタスクのために設計されていること
- 直接実行は、シンプルでスコープの明確な変更に適していること（例：1つの関数への単一のバリデーションチェックの追加）
- プランモードは、変更を確定する前に安全なコードベースの探索と設計を可能にし、コストのかかる手戻りを防ぐこと
- メインの会話コンテキストを保持するために、冗長な発見過程の出力を分離してサマリーを返すExploreサブエージェント

**スキル:**
- アーキテクチャ上の影響を伴うタスク（例：マイクロサービスの再構成、45以上のファイルに影響するライブラリの移行、異なるインフラ要件を持つ統合アプローチ間の選択）に対するプランモードの選択
- スコープが明確で十分に理解された変更（例：明確なスタックトレースを持つ単一ファイルのバグ修正、日付バリデーションの条件分岐の追加）に対する直接実行の選択
- 複数フェーズのタスク中にコンテキストウィンドウの枯渇を防ぐための、冗長な発見フェーズにおけるExploreサブエージェントの使用
- 調査のためのプランモードと実装のための直接実行の組み合わせ（例：ライブラリ移行を計画してから、計画したアプローチを実行する）

### Task Statement 3.5: 段階的な改善のための反復的な改善技法の適用

**知識:**
- 散文による説明が一貫性なく解釈される場合に、期待される変換を伝える最も効果的な方法としての具体的な入出力例
- テスト駆動の反復：まずテストスイートを書き、テストの失敗を共有することで段階的な改善を導く
- 実装前に、開発者が想定していなかった考慮事項を明らかにするために、Claudeに質問をさせるインタビューパターン
- 単一のメッセージですべての問題を提供すべき場合（相互作用する問題）と、順次修正すべき場合（独立した問題）

**スキル:**
- 自然言語による説明が一貫性のない結果を生む場合に、変換要件を明確にするための2〜3個の具体的な入出力例の提供
- 実装前に、期待される挙動、エッジケース、パフォーマンス要件をカバーするテストスイートを作成し、テストの失敗を共有することで反復すること
- 馴染みのないドメインで解決策を実装する前に、設計上の考慮事項（例：キャッシュ無効化戦略、失敗モード）を明らかにするためのインタビューパターンの使用
- エッジケースの処理を修正するために、入力例と期待される出力を伴う具体的なテストケースを提供すること（例：マイグレーションスクリプトにおけるnull値）
- 修正が相互作用する場合には単一の詳細なメッセージで複数の相互作用する問題に対処し、独立した問題については順次反復すること

### Task Statement 3.6: Claude CodeのCI/CDパイプラインへの統合

**知識:**
- 自動化されたパイプラインでClaude Codeを非対話モードで実行するための`-p`（または`--print`）フラグ
- CIコンテキストで構造化出力を強制するための`--output-format json`および`--json-schema`のCLIフラグ
- CIから呼び出されるClaude Codeにプロジェクトコンテキスト（テスト標準、フィクスチャの規約、レビュー基準）を提供するメカニズムとしてのCLAUDE.md
- セッションコンテキストの分離：コードを生成した同じClaudeセッションが、独立したレビューインスタンスと比較して自身の変更をレビューする際に効果が低い理由

**スキル:**
- 対話的な入力によるハングを防ぐために、`-p`フラグを用いてCIでClaude Codeを実行すること
- 自動的にインラインPRコメントとして投稿するための機械可読な構造化された調査結果を生成するために、`--output-format json`を`--json-schema`とともに使用すること
- 新しいコミットの後にレビューを再実行する際、重複するコメントを避けるために新規または未対応の問題のみを報告するようClaudeに指示し、以前のレビューの調査結果をコンテキストに含めること
- テスト生成が既にテストスイートでカバーされている重複したシナリオを提案しないように、既存のテストファイルをコンテキストに提供すること
- テスト生成の品質を向上させ、低価値なテスト出力を減らすために、テスト標準、価値のあるテスト基準、利用可能なフィクスチャをCLAUDE.mdに文書化すること

## Domain 4: Prompt Engineering & Structured Output（プロンプトエンジニアリングと構造化出力）

### Task Statement 4.1: 精度を向上させ誤検知を減らすための明示的な基準を持つプロンプトの設計

**知識:**
- 曖昧な指示よりも明示的な基準を用いることの重要性（例：「コメントの正確性を確認する」よりも「主張された挙動が実際のコードの挙動と矛盾する場合にのみコメントにフラグを立てる」）
- 「保守的であること」や「確信度の高い調査結果のみを報告する」といった一般的な指示が、具体的なカテゴリ基準と比較して精度の向上に失敗する理由
- 開発者の信頼に対する誤検知率の影響：誤検知率の高いカテゴリは、正確なカテゴリに対する信頼も損なうこと

**スキル:**
- 確信度に基づくフィルタリングに頼るのではなく、報告すべき問題（バグ、セキュリティ）とスキップすべき問題（軽微なスタイル、ローカルなパターン）を定義する具体的なレビュー基準の作成
- そのカテゴリのプロンプトを改善しながら開発者の信頼を回復するために、誤検知率の高いカテゴリを一時的に無効化すること
- 一貫した分類を達成するために、各重大度レベルの具体的なコード例を伴う明示的な重大度基準の定義

### Task Statement 4.2: 出力の一貫性と品質を向上させるためのFew-shotプロンプティングの適用

**知識:**
- 詳細な指示だけでは一貫性のない結果が生じる場合に、一貫してフォーマットされた実行可能な出力を達成するための最も効果的な技法としてのfew-shot例
- 曖昧なケースの処理を示すfew-shot例の役割（例：曖昧なリクエストに対するツール選択、ブランチレベルのテストカバレッジのギャップ）
- 事前に指定されたケースのみに一致させるのではなく、モデルが新しいパターンに判断を汎化できるようにするfew-shot例の仕組み
- 抽出タスクにおける幻覚（hallucination）を減らすためのfew-shot例の有効性（例：非公式な計測値や多様なドキュメント構造の処理）

**スキル:**
- もっともらしい代替案よりもあるアクションが選ばれた理由を示す推論を伴う、曖昧なシナリオのための2〜4個の対象を絞ったfew-shot例の作成
- 一貫性を達成するために、望ましい特定の出力形式（場所、問題、重大度、提案される修正）を示すfew-shot例を含めること
- 誤検知を減らしつつ汎化を可能にするために、許容可能なコードパターンと真の問題とを区別するfew-shot例を提供すること
- 多様なドキュメント構造（インライン引用 vs 参考文献リスト、方法論のセクション vs 埋め込まれた詳細）の正しい処理を示すためのfew-shot例の使用
- 必須フィールドの空／null抽出に対処するために、多様な形式のドキュメントからの正しい抽出を示すfew-shot例の追加

### Task Statement 4.3: ツール使用とJSONスキーマを用いた構造化出力の強制

**知識:**
- スキーマ準拠が保証された構造化出力を得るための最も信頼性の高いアプローチとしての、JSONスキーマを伴うツール使用（`tool_use`）——JSON構文エラーを排除する
- `tool_choice: "auto"`（モデルはツールを呼び出す代わりにテキストを返す場合がある）、`"any"`（モデルはツールを呼び出さなければならないがどれを呼び出すかは選択できる）、強制的なツール選択（モデルは特定の名前付きツールを呼び出さなければならない）の違い
- ツール使用による厳密なJSONスキーマは構文エラーを排除するが、意味的なエラー（例：明細項目が合計と一致しない、値が誤ったフィールドに入っている）は防げないこと
- スキーマ設計上の考慮事項：必須フィールド vs 任意フィールド、拡張可能なカテゴリのための「other」+ 詳細文字列パターンを持つenumフィールド

**スキル:**
- 入力パラメータとしてJSONスキーマを持つ抽出ツールを定義し、`tool_use`レスポンスから構造化データを抽出すること
- 複数の抽出スキーマが存在し、ドキュメントの種類が不明な場合に構造化出力を保証するために`tool_choice: "any"`を設定すること
- エンリッチメントのステップの前に特定の抽出が実行されるようにするために、`tool_choice: {"type": "tool", "name": "extract_metadata"}`で特定のツールを強制すること
- ソースドキュメントにその情報が含まれない場合がある際、モデルが必須フィールドを満たすために値を捏造するのを防ぐために、スキーマフィールドを任意（null許容）として設計すること
- 曖昧なケースのために`"unclear"`のようなenum値を追加し、拡張可能な分類のために`"other"`+ 詳細フィールドを追加すること
- 一貫性のないソースの書式に対応するために、厳密な出力スキーマとともに書式正規化ルールをプロンプトに含めること

### Task Statement 4.4: 抽出品質のための検証・リトライ・フィードバックループの実装

**知識:**
- エラーフィードバック付きリトライ：モデルを修正へ導くために、リトライ時に特定の検証エラーをプロンプトに追加すること
- リトライの限界：必要な情報がソースドキュメントに単に存在しない場合（書式や構造上のエラーとは対照的に）、リトライは効果がないこと
- フィードバックループの設計：どのコードコンストラクトが調査結果を引き起こすかを追跡すること（`detected_pattern`フィールド）で、却下パターンの体系的な分析を可能にすること
- 意味的な検証エラー（値が合計と一致しない、フィールドの配置が誤っている）とスキーマ構文エラー（ツール使用によって排除される）の違い

**スキル:**
- 元のドキュメント、失敗した抽出、特定の検証エラーを含む、モデルによる自己修正のためのフォローアップリクエストの実装
- リトライが効果的でない場合（例：情報が提供されていない外部ドキュメントにのみ存在する場合）と、成功する場合（書式の不一致、構造的な出力エラー）とを識別すること
- 開発者が調査結果を却下したときの誤検知パターンの分析を可能にするために、構造化された調査結果に`detected_pattern`フィールドを追加すること
- 自己修正の検証フローの設計：不一致にフラグを立てるために`stated_total`とともに`calculated_total`を抽出すること、一貫性のないソースデータのために`conflict_detected`のブール値を追加すること

### Task Statement 4.5: 効率的なバッチ処理戦略の設計

**知識:**
- Message Batches API：50%のコスト削減、最大24時間の処理ウィンドウ、保証されたレイテンシSLAなし
- バッチ処理は、ノンブロッキングでレイテンシに寛容なワークロード（夜間レポート、週次監査、夜間テスト生成）には適しており、ブロッキングワークフロー（マージ前チェック）には不適であること
- バッチAPIは、単一のリクエスト内での複数ターンのツール呼び出しをサポートしないこと（リクエストの途中でツールを実行して結果を返すことはできない）
- バッチのリクエスト／レスポンスのペアを関連付けるための`custom_id`フィールド

**スキル:**
- ワークフローのレイテンシ要件にAPIアプローチを合わせること：ブロッキングのマージ前チェックには同期API、夜間・週次分析にはバッチAPI
- SLAの制約に基づくバッチ送信頻度の計算（例：24時間のバッチ処理で30時間のSLAを保証するための4時間ウィンドウ）
- バッチの失敗への対応：（`custom_id`で識別された）失敗したドキュメントのみを、適切な修正（例：コンテキスト上限を超えたドキュメントのチャンク化）を加えて再送すること
- 大量のドキュメントをバッチ処理する前に、サンプルセットでプロンプトの改善を行い、初回成功率を最大化し反復的な再送コストを削減すること

### Task Statement 4.6: 複数インスタンス・複数パスのレビューアーキテクチャの設計

**知識:**
- 自己レビューの限界：モデルは生成時の推論コンテキストを保持しているため、同じセッション内で自身の判断に疑問を持ちにくいこと
- （事前の推論コンテキストを持たない）独立したレビューインスタンスは、自己レビューの指示や拡張思考よりも微妙な問題を捉えるのに効果的であること
- 複数パスレビュー：注意力の希釈と矛盾する調査結果を避けるために、大規模なレビューをファイルごとのローカル分析パスとクロスファイル統合パスに分割すること

**スキル:**
- 生成側の推論コンテキストを持たない2つ目の独立したClaudeインスタンスを使って生成されたコードをレビューすること
- 大規模な複数ファイルレビューを、ローカルな問題のためのファイルごとの集中パスと、クロスファイルのデータフロー分析のための別途の統合パスに分割すること
- 較正されたレビューのルーティングを可能にするために、モデルが各調査結果とともに確信度を自己報告する検証パスの実行

## Domain 5: Context Management & Reliability（コンテキスト管理と信頼性）

### Task Statement 5.1: 長い対話にわたって重要な情報を保持するための会話コンテキストの管理

**知識:**
- 段階的な要約（progressive summarization）のリスク：数値、パーセンテージ、日付、顧客が述べた期待値を曖昧なサマリーに凝縮してしまうこと
- 「lost in the middle（ミドルロスト）」効果：モデルは長い入力の先頭と末尾の情報は確実に処理するが、中間部分の調査結果を見落とす可能性があること
- ツールの結果がコンテキストに蓄積し、その関連性に対して不釣り合いにトークンを消費する方法（例：注文照会あたり40以上のフィールドのうち、関連するのはわずか5個の場合）
- 会話の一貫性を保つために、後続のAPIリクエストで完全な会話履歴を渡すことの重要性

**スキル:**
- 要約された履歴の外側で、各プロンプトに含まれる永続的な「ケースファクト」ブロックに、取引上の事実（金額、日付、注文番号、ステータス）を抽出すること
- 複数の課題にまたがるセッションのために、構造化された課題データ（注文ID、金額、ステータス）を別のコンテキストレイヤーに抽出・保持すること
- コンテキストに蓄積する前に、冗長なツール出力を関連するフィールドのみにトリムすること（例：注文照会から返品に関連するフィールドのみを保持する）
- 位置の影響を緩和するために、集約された入力の先頭に主要な調査結果のサマリーを配置し、明示的なセクション見出しで詳細な結果を整理すること
- 正確な下流の統合をサポートするために、サブエージェントに構造化された出力にメタデータ（日付、ソースの場所、方法論的な文脈）を含めることを要求すること
- 下流のエージェントのコンテキスト予算が限られている場合、上流のエージェントを、冗長なコンテンツや推論チェーンではなく構造化されたデータ（主要な事実、引用、関連度スコア）を返すように変更すること

### Task Statement 5.2: 効果的なエスカレーションと曖昧性解決パターンの設計

**知識:**
- 適切なエスカレーションのトリガー：人間対応を求める顧客のリクエスト、ポリシーの例外／欠落（単に複雑なケースというだけではなく）、意味のある進展ができないこと
- 顧客が明示的に要求した場合に即座にエスカレーションすることと、問題が単純な場合に解決を申し出ることとの違い
- 感情に基づくエスカレーションと自己申告された確信度スコアが、実際のケースの複雑さに対する信頼性の低い代理指標である理由
- 複数の顧客の一致がある場合、ヒューリスティックな選択ではなく（追加の識別情報を要求する）明確化を必要とする理由

**スキル:**
- いつエスカレーションし、いつ自律的に解決すべきかを示すfew-shot例とともに、明示的なエスカレーション基準をシステムプロンプトに追加すること
- まず調査を試みることなく、人間のエージェントに対する顧客の明示的な要求に即座に応じること
- 問題がエージェントの能力の範囲内である場合、フラストレーションを認めつつ解決を申し出て、顧客が希望を繰り返した場合にのみエスカレーションすること
- ポリシーが顧客の特定のリクエストについて曖昧または沈黙している場合にエスカレーションすること（例：ポリシーが自社サイトの価格調整のみを扱っている場合の競合他社の価格マッチング）
- ツールの結果が複数の一致を返した場合、ヒューリスティックに基づいて選択するのではなく、追加の識別情報を求めるようエージェントに指示すること

### Task Statement 5.3: マルチエージェントシステム全体でのエラー伝播戦略の実装

**知識:**
- コーディネーターの知的な回復判断を可能にする、構造化されたエラーコンテキスト（失敗の種類、試みたクエリ、部分的な結果、代替アプローチ）
- アクセス失敗（再試行の判断が必要なタイムアウト）と有効な空の結果（一致なしの成功したクエリ）の違い
- 一般的なエラーステータス（「検索が利用できません」）がコーディネーターから貴重なコンテキストを隠してしまう理由
- エラーを静かに抑制すること（空の結果を成功として返すこと）や、単一の失敗でワークフロー全体を終了させることが、どちらもアンチパターンである理由

**スキル:**
- コーディネーターの回復を可能にするために、失敗の種類、試みたこと、部分的な結果、潜在的な代替案を含む構造化されたエラーコンテキストの返却
- コーディネーターが適切な判断を下せるように、エラー報告においてアクセス失敗と有効な空の結果を区別すること
- サブエージェントに一時的な障害に対するローカルな回復を実装させ、解決できないエラーのみを、試みたことと部分的な結果とともに伝播させること
- どの調査結果がよくサポートされているか、どのトピック領域が利用できないソースによりギャップがあるかを示すカバレッジ注釈を用いて統合出力を構造化すること

### Task Statement 5.4: 大規模なコードベース探索におけるコンテキストの効果的な管理

**知識:**
- 長時間のセッションにおけるコンテキストの劣化：モデルが一貫性のない回答をし始め、以前に発見された特定のクラスではなく「典型的なパターン」を参照するようになること
- コンテキスト境界をまたいで主要な調査結果を永続化させるスクラッチパッドファイルの役割
- メインエージェントが高レベルの理解を調整する一方で、冗長な探索出力を分離するためのサブエージェントへの委譲
- クラッシュリカバリのための構造化された状態の永続化：各エージェントが既知の場所に状態をエクスポートし、コーディネーターが再開時にマニフェストを読み込むこと

**スキル:**
- メインエージェントが高レベルの調整を保持する一方で、特定の質問（例：「すべてのテストファイルを見つける」「返金フローの依存関係をトレースする」）を調査するサブエージェントのスポーン
- コンテキストの劣化に対抗するために、主要な調査結果を記録するスクラッチパッドファイルをエージェントに維持させ、後続の質問のためにそれらを参照させること
- 次のフェーズのサブエージェントをスポーンする前に、あるフェーズの主要な調査結果を要約し、初期コンテキストにサマリーを注入すること
- コーディネーターが再開時に読み込みエージェントのプロンプトに注入する、構造化されたエージェント状態のエクスポート（マニフェスト）を用いたクラッシュリカバリの設計
- 冗長な発見の出力でコンテキストが満杯になった場合、長時間の探索セッション中にコンテキスト使用量を削減するための`/compact`の使用

### Task Statement 5.5: 人間によるレビューワークフローと確信度較正の設計

**知識:**
- 集約された精度指標（例：全体で97%）が、特定のドキュメントの種類やフィールドにおける低いパフォーマンスを隠してしまうリスク
- 高確信度の抽出における誤り率の測定と新しい誤りパターンの検出のための層化無作為抽出
- レビュー対応の振り分けのための、ラベル付き検証セットを用いて較正されたフィールドレベルの確信度スコア
- 高確信度の抽出を自動化する前に、ドキュメントの種類とフィールドのセグメントごとに精度を検証することの重要性

**スキル:**
- 継続的な誤り率の測定と新しいパターンの検出のための、高確信度抽出の層化無作為抽出の実装
- 人間によるレビューを減らす前に、すべてのセグメントにわたって一貫したパフォーマンスを確認するための、ドキュメントの種類とフィールドごとの精度分析
- モデルにフィールドレベルの確信度スコアを出力させ、ラベル付き検証セットを用いてレビュー閾値を較正すること
- 限られたレビュー担当者のキャパシティを優先するために、モデルの確信度が低い、または曖昧・矛盾するソースドキュメントを持つ抽出を人間によるレビューにルーティングすること

### Task Statement 5.6: 複数ソースの統合における情報の来歴の保持と不確実性の処理

**知識:**
- 主張とソースのマッピングを保持せずに調査結果が圧縮される要約のステップで、ソースの帰属が失われる方法
- 統合エージェントが調査結果を組み合わせる際に保持・マージしなければならない、構造化された主張とソースのマッピングの重要性
- 信頼できるソース間で矛盾する統計値の扱い方：値を恣意的に選択するのではなく、ソースの帰属とともに矛盾に注釈を付けること
- 時間的なデータ：時間的な差異が矛盾として誤って解釈されるのを防ぐために、構造化された出力に発行日／収集日を要求すること

**スキル:**
- 下流のエージェントが統合を通じて保持する構造化された主張とソースのマッピング（ソースURL、ドキュメント名、関連する抜粋）をサブエージェントに出力させること
- 十分に確立された調査結果と論争のある調査結果とを区別する明示的なセクションでレポートを構成し、元のソースの特徴付けと方法論的な文脈を保持すること
- 矛盾する値を含め明示的に注釈を付けたままドキュメント分析を完了し、統合に渡す前にどのように調整するかをコーディネーターに決定させること
- 正しい時間的解釈を可能にするために、構造化された出力に発行日または収集日を含めることをサブエージェントに要求すること
- すべてを均一な形式に変換するのではなく、統合出力において異なるコンテンツタイプを適切にレンダリングすること——財務データは表として、ニュースは文章として、技術的な調査結果は構造化されたリストとして

## 準備の方法

この認定試験の準備のために：

- **Claude Agent SDKでエージェントを構築する**：ツール呼び出し、エラーハンドリング、セッション管理を伴う完全なエージェント型ループを実装する。サブエージェントをスポーンし、それらの間でコンテキストを受け渡す練習をする。
- **実際のプロジェクトのためにClaude Codeを設定する**：設定階層を持つCLAUDE.mdをセットアップし、`.claude/rules/`にパス固有のルールを作成し、フロントマターオプション（`context: fork`、`allowed-tools`）を持つカスタムスキルを構築し、少なくとも1つのMCPサーバーを統合する。
- **MCPツールを設計・テストする**：類似したツールを明確に区別するツールの説明を書く。エラーカテゴリと再試行可能フラグを持つ構造化されたエラーレスポンスを実装する。曖昧なリクエストでツール選択の信頼性をテストする。
- **構造化データ抽出パイプラインを構築する**：JSONスキーマとともに`tool_use`を使用し、検証・リトライループを実装し、任意／null許容フィールドを持つスキーマを設計し、Message Batches APIを用いたバッチ処理を練習する。
- **プロンプトエンジニアリング技法を練習する**：曖昧なシナリオのためのfew-shot例を書く。誤検知を減らすための明示的なレビュー基準を定義する。大規模なコードレビューのための複数パスレビューアーキテクチャを設計する。
- **コンテキスト管理パターンを学ぶ**：冗長なツール出力から構造化された事実を抽出する練習、長時間のセッションのためのスクラッチパッドファイルの実装、コンテキスト上限を管理するためのサブエージェントへの委譲の設計を行う。
- **エスカレーションとhuman-in-the-loopのパターンを復習する**：いつエスカレーションすべきか（ポリシーの欠落、顧客のリクエスト、進展できないこと）と、いつ自律的に解決すべきかを理解する。確信度に基づくルーティングを伴う人間によるレビューワークフローの設計を練習する。

## 準備のための演習

以下の実践的な演習に取り組むことで、試験で扱われるトピックに関する実践的な習熟度を身につけてください。各演習は、1つまたは複数の試験ドメインにわたる知識を強化するように設計されています。

### 演習1: エスカレーションロジックを持つマルチツールエージェントの構築

**目的:** ツール統合、構造化されたエラーハンドリング、エスカレーションパターンを伴うエージェント型ループの設計を練習する。

**手順:**
- 各ツールの目的、想定される入力、境界条件を明確に区別する詳細な説明を持つ、3〜4個のMCPツールを定義する。選択の混乱を避けるために慎重な説明が必要な、類似した機能を持つツールを少なくとも2つ含める。
- ツール実行を継続するか最終的な応答を提示するかを判断するために`stop_reason`を確認する、エージェント型ループを実装する。`"tool_use"`と`"end_turn"`の両方の停止理由を正しく処理する。
- ツールに構造化されたエラーレスポンスを追加する：`errorCategory`（一時的／検証／権限）、`isRetryable`のブール値、人間が読める説明を含める。エージェントが各エラータイプを適切に処理することをテストする（一時的なエラーの再試行、ビジネスエラーのユーザーへの説明）。
- ビジネスルール（例：一定の閾値額を超える操作をブロックする）を強制するツール呼び出しを傍受するプログラム的なフックを実装し、トリガーされた場合にエスカレーションワークフローにリダイレクトする。
- 複数の懸念事項を含むメッセージ（例：複数の問題を含むリクエスト）でテストし、エージェントがリクエストを分解し、各懸念事項を処理し、統一された応答に統合することを検証する。

**強化されるドメイン:** Domain 1（Agentic Architecture & Orchestration）、Domain 2（Tool Design & MCP Integration）、Domain 5（Context Management & Reliability）

### 演習2: チーム開発ワークフローのためのClaude Codeの設定

**目的:** 複数開発者向けプロジェクトのために、CLAUDE.md階層、カスタムスラッシュコマンド、パス固有ルール、MCPサーバー統合の設定を練習する。

**手順:**
- 普遍的なコーディング標準とテストの規約を持つプロジェクトレベルのCLAUDE.mdを作成する。プロジェクトレベルに配置された指示が、すべてのチームメンバーに一貫して適用されることを確認する。
- 異なるコード領域向けのYAMLフロントマターのglobパターンを持つ`.claude/rules/`ファイルを作成する（例：APIの規約向けに`paths: ["src/api/**/*"]`、テストの規約向けに`paths: ["**/*.test.*"]`）。一致するファイルを編集する際にのみルールが読み込まれることをテストする。
- `context: fork`と`allowed-tools`の制限を持つ、`.claude/skills/`内のプロジェクトスコープのスキルを作成する。スキルがメインの会話コンテキストを汚染することなく隔離された状態で実行されることを検証する。
- 認証情報のための環境変数展開を伴うMCPサーバーを`.mcp.json`に設定する。`~/.claude.json`に個人の実験的なMCPサーバーを追加し、両方が同時に利用可能であることを検証する。
- さまざまな複雑さのタスクでプランモードと直接実行をテストする：単一ファイルのバグ修正、複数ファイルにわたるライブラリの移行、複数の有効な実装アプローチを持つ新機能。プランモードがいつ価値を提供するかを観察する。

**強化されるドメイン:** Domain 3（Claude Code Configuration & Workflows）、Domain 2（Tool Design & MCP Integration）

### 演習3: 構造化データ抽出パイプラインの構築

**目的:** JSONスキーマの設計、構造化出力のための`tool_use`の使用、検証・リトライループの実装、バッチ処理戦略の設計を練習する。

**手順:**
- 必須フィールドと任意フィールド、「other」+ 詳細文字列パターンを持つenum、ソースドキュメントに存在しない可能性のある情報のためのnull許容フィールドを含むJSONスキーマを持つ抽出ツールを定義する。一部のフィールドが欠落しているドキュメントを処理し、モデルが値を捏造するのではなくnullを返すことを検証する。
- 検証・リトライループを実装する：PydanticまたはJSONスキーマの検証が失敗した場合、ドキュメント、失敗した抽出、特定の検証エラーを含むフォローアップリクエストを送信する。リトライによって解決可能なエラー（書式の不一致）と解決不可能なエラー（ソースに情報が存在しない）を追跡する。
- さまざまな形式のドキュメント（例：インライン引用 vs 参考文献リスト、物語形式の説明 vs 構造化された表）からの抽出を示すfew-shot例を追加し、構造的な多様性への対応の改善を検証する。

- 人間によるレビューのルーティング戦略を実装する：モデルにフィールドレベルの確信度スコアを出力させ、確信度の低い抽出を人間によるレビューにルーティングし、ドキュメントの種類とフィールドごとに精度を分析して一貫したパフォーマンスを検証する。

**強化されるドメイン:** Domain 4（Prompt Engineering & Structured Output）、Domain 5（Context Management & Reliability）

### 演習4: マルチエージェントリサーチパイプラインの設計とデバッグ

**目的:** サブエージェントのオーケストレーション、コンテキストの受け渡しの管理、エラー伝播の実装、来歴追跡を伴う統合の処理を練習する。

**手順:**
- 少なくとも2つのサブエージェント（例：Web検索とドキュメント分析）に委譲するコーディネーターエージェントを構築する。コーディネーターの`allowedTools`に`"Task"`が含まれていること、各サブエージェントが自動的なコンテキスト継承に頼るのではなく、そのプロンプトの中で直接調査結果を受け取ることを確認する。
- コーディネーターが単一の応答内で複数のTaskツール呼び出しを発行することで、並列サブエージェント実行を実装する。順次実行と比較したレイテンシの改善を測定する。
- コンテンツとメタデータを分離するサブエージェントの構造化出力を設計する：各調査結果は、主張、証拠となる抜粋、ソースURL／ドキュメント名、発行日を含むべきである。統合サブエージェントが調査結果を組み合わせる際にソースの帰属を保持することを検証する。
- エラー伝播を実装する：サブエージェントのタイムアウトをシミュレートし、コーディネーターが構造化されたエラーコンテキスト（失敗の種類、試みたクエリ、部分的な結果）を受け取ることを検証する。コーディネーターが部分的な結果で処理を続行し、最終出力にカバレッジのギャップを注釈できることをテストする。
- 矛盾するソースデータ（例：異なる統計値を持つ2つの信頼できるソース）でテストし、統合出力が恣意的に1つを選ぶのではなく、ソースの帰属とともに両方の値を保持すること、また十分に確立された調査結果と論争のある調査結果を区別するようにレポートが構成されることを検証する。

**強化されるドメイン:** Domain 1（Agentic Architecture & Orchestration）、Domain 2（Tool Design & MCP Integration）、Domain 5（Context Management & Reliability）

### シナリオ: Customer Support Resolution Agent

#### Question 1

本番データによると、12%のケースであなたのエージェントは`get_customer`を完全にスキップし、顧客が述べた名前のみを使って`lookup_order`を呼び出しており、時にアカウントの誤認識や誤った返金につながっています。この信頼性の問題に最も効果的に対処する変更は何ですか？

- A. `get_customer`が検証済みの顧客IDを返すまで、`lookup_order`と`process_refund`の呼び出しをブロックするプログラム的な前提条件を追加する。
- B. 注文操作の前に`get_customer`による顧客確認が必須であることを明記するようシステムプロンプトを強化する。
- C. 顧客が注文の詳細を自発的に提供した場合でも、エージェントが常に`get_customer`を最初に呼び出すことを示すfew-shot例を追加する。
- D. 各リクエストを分析し、そのリクエストタイプに適したツールのサブセットのみを有効にするルーティング分類器を実装する。

**正解: A.** （返金処理前の顧客確認のような）重要なビジネスロジックのために特定のツールシーケンスが要求される場合、プログラム的な強制はプロンプトベースのアプローチでは得られない決定論的な保証を提供する。選択肢BとCは確率的なLLMの遵守に依存しており、エラーが金銭的な結果をもたらす場合には不十分である。選択肢Dはツールの順序ではなくツールの可用性に対処しており、これは実際の問題ではない。

#### Question 2

本番ログによると、エージェントはユーザーが注文について尋ねたとき（例：「注文番号12345を確認して」）、`lookup_order`ではなく`get_customer`を頻繁に呼び出しています。両方のツールには最小限の説明（「顧客情報を取得する」／「注文の詳細を取得する」）しかなく、類似した識別子の形式を受け付けます。ツール選択の信頼性を改善するために最も効果的な最初のステップは何ですか？

- A. 注文関連のクエリが`lookup_order`にルーティングされることを示す5〜8個の例とともに、正しいツール選択のパターンを示すfew-shot例をシステムプロンプトに追加する。
- B. 各ツールの説明を拡張し、それが処理する入力形式、クエリの例、エッジケース、類似ツールに対していつ使うべきかを説明する境界を含める。
- C. 各ターンの前にユーザー入力を解析し、検出されたキーワードと識別子のパターンに基づいて適切なツールを事前選択するルーティングレイヤーを実装する。
- D. 両方のツールを、任意の識別子を受け付け内部的にどのバックエンドに問い合わせるかを判断する単一の`lookup_entity`ツールに統合する。

**正解: B.** ツールの説明は、LLMがツール選択に用いる主要なメカニズムである。説明が最小限である場合、モデルは類似したツールを区別するためのコンテキストを欠いている。選択肢Bは、この根本原因に、低労力かつ高レバレッジな修正で直接対処している。few-shot例（A）は根本的な問題を修正することなくトークンのオーバーヘッドを追加する。ルーティングレイヤー（C）は過剰設計であり、LLMの自然言語理解を迂回してしまう。ツールの統合（D）は有効なアーキテクチャ上の選択ではあるが、直近の問題が不十分な説明であるときに「最初のステップ」として要求されるより多くの労力を必要とする。

#### Question 3

あなたのエージェントは初回接触解決率55%を達成しており、目標の80%を大きく下回っています。ログによると、（写真証拠付きの標準的な破損交換のような）単純なケースをエスカレーションする一方で、ポリシーの例外を必要とする複雑な状況を自律的に処理しようとしています。エスカレーションの較正を改善する最も効果的な方法は何ですか？

- A. いつエスカレーションし、いつ自律的に解決すべきかを示すfew-shot例とともに、明示的なエスカレーション基準をシステムプロンプトに追加する。
- B. エージェントに各応答の前に確信度スコア（1〜10）を自己申告させ、確信度が閾値を下回った場合に自動的にリクエストを人間にルーティングする。
- C. 過去のチケットで訓練された別の分類器モデルをデプロイし、メインエージェントが処理を開始する前にどのリクエストがエスカレーションを必要とするかを予測させる。
- D. 顧客のフラストレーションのレベルを検出するために感情分析を実装し、ネガティブな感情が閾値を超えた場合に自動的にエスカレーションする。

**正解: A.** 明示的なエスカレーション基準をfew-shot例とともに追加することは、根本原因である不明確な判断境界に直接対処する。これはインフラを追加する前の、釣り合いの取れた最初の対応である。選択肢Bは、LLMが自己申告する確信度が十分に較正されていないため失敗する——エージェントは既に難しいケースにおいて誤って自信を持っている。選択肢Cは過剰設計であり、プロンプトの最適化が試みられていないのにラベル付きデータとML基盤を要求する。選択肢Dはまったく別の問題を解決している。感情は、実際の問題であるケースの複雑さとは相関しない。

### シナリオ: Code Generation with Claude Code

#### Question 4

あなたのチームの標準的なコードレビューチェックリストを実行する、カスタムの`/review`スラッシュコマンドを作成したいと考えています。このコマンドは、開発者がリポジトリをクローンまたはプルしたときに、すべての開発者が利用できる必要があります。このコマンドファイルはどこに作成すべきですか？

- A. プロジェクトリポジトリ内の`.claude/commands/`ディレクトリ
- B. 各開発者のホームディレクトリの`~/.claude/commands/`
- C. プロジェクトルートのCLAUDE.mdファイル
- D. commands配列を持つ`.claude/config.json`ファイル

**正解: A.** プロジェクトスコープのカスタムスラッシュコマンドは、リポジトリ内の`.claude/commands/`ディレクトリに保存すべきである。これらのコマンドはバージョン管理され、開発者がリポジトリをクローンまたはプルしたときに自動的にすべての開発者が利用できる。選択肢B（`~/.claude/commands/`）は、バージョン管理を通じて共有されない個人用コマンドのためのものである。選択肢C（CLAUDE.md）は、コマンド定義ではなく、プロジェクトの指示とコンテキストのためのものである。選択肢Dは、Claude Codeに存在しない設定メカニズムを説明している。

#### Question 5

あなたはチームのモノリシックなアプリケーションをマイクロサービスに再構成する担当に任命されました。これには数十のファイルにわたる変更が伴い、サービス境界とモジュール依存関係に関する決定が必要です。どのアプローチを取るべきですか？

- A. コードベースを探索し、依存関係を理解し、変更を行う前に実装アプローチを設計するために、プランモードに入る。
- B. 直接実行から始めて段階的に変更を加え、実装が自然なサービス境界を明らかにするようにする。
- C. 各サービスがどのように構成されるべきかを正確に詳述した包括的な事前指示とともに、直接実行を使用する。
- D. 直接実行モードで開始し、実装中に予期しない複雑さに遭遇した場合にのみプランモードに切り替える。

**正解: A.** プランモードは、大規模な変更、複数の有効なアプローチ、アーキテクチャ上の決定を伴う複雑なタスクのために設計されており——これはまさに、モノリスからマイクロサービスへの再構成が要求するものである。これにより、変更を確定する前に安全なコードベースの探索と設計が可能になる。選択肢Bは、依存関係が遅れて発見された場合にコストのかかる手戻りのリスクを負う。選択肢Cは、コードを探索せずに正しい構造を既に知っていると仮定している。選択肢Dは、複雑さが後で発生しうるものではなく、既に要件の中で述べられていることを無視している。

#### Question 6

あなたのコードベースには、異なるコーディング規約を持つ明確に区別された領域があります：Reactコンポーネントはhooksを用いた関数型スタイルを、APIハンドラーは特定のエラーハンドリングを伴うasync/awaitを、データベースモデルはリポジトリパターンに従っています。テストファイルはコードベース全体に、テスト対象のコードのすぐそばに配置されており（例：`Button.tsx`の隣に`Button.test.tsx`）、場所に関わらずすべてのテストが同じ規約に従うことを望んでいます。Claudeがコード生成時に正しい規約を自動的に適用することを保証する、最も保守性の高い方法は何ですか？

- A. YAMLフロントマターでglobパターンを指定し、ファイルパスに基づいて条件付きで規約を適用する、`.claude/rules/`内のルールファイルを作成する。
- B. すべての規約を各領域のヘッダーの下にルートのCLAUDE.mdファイルに統合し、どのセクションが適用されるかをClaudeの推論に委ねる。
- C. 各コードタイプ向けのスキルを`.claude/skills/`に作成し、それぞれのSKILL.mdファイルに関連する規約を含める。
- D. 各サブディレクトリに、その領域固有の規約を含む個別のCLAUDE.mdファイルを配置する。

**正解: A.** 選択肢Aが正解である。なぜなら、globパターン（例：`**/*.test.tsx`）を持つ`.claude/rules/`は、ディレクトリの場所に関わらずファイルパスに基づいて規約を自動的に適用することを可能にし、コードベース全体に分散したテストファイルにとって不可欠だからである。選択肢Bは明示的なマッチングではなく推論に依存しており、信頼性に欠ける。選択肢Cは手動でのスキル呼び出しを必要とするか、Claudeがそれらを読み込むことを選ぶことに依存しており、ファイルパスに基づいた決定論的な「自動」適用の必要性と矛盾する。選択肢Dは、CLAUDE.mdファイルがディレクトリに紐づいているため、多くのディレクトリに分散したファイルを容易に扱うことができない。

### シナリオ: Multi-Agent Research System

- B. コーディネーターエージェントのタスク分解が狭すぎるため、トピックの関連するすべての領域をカバーしないサブエージェントの割り当てになっている。

#### Question 8

Web検索サブエージェントが複雑なトピックを調査中にタイムアウトしました。この失敗情報がどのようにコーディネーターエージェントに伝わるかを設計する必要があります。知的な回復を最も可能にするエラー伝播アプローチはどれですか？

- A. 失敗の種類、試みたクエリ、部分的な結果、潜在的な代替アプローチを含む構造化されたエラーコンテキストをコーディネーターに返す。
- B. サブエージェント内で指数バックオフによる自動リトライロジックを実装し、すべてのリトライが尽きた後にのみ一般的な「検索利用不可」ステータスを返す。
- C. サブエージェント内でタイムアウトをキャッチし、成功としてマークされた空の結果セットを返す。
- D. タイムアウト例外を、リサーチワークフロー全体を終了させるトップレベルのハンドラーに直接伝播する。

**正解: A.** 構造化されたエラーコンテキストは、コーディネーターが知的な回復判断——修正したクエリで再試行するか、別のアプローチを試すか、部分的な結果で処理を続行するか——を下すために必要な情報を与える。選択肢Bの一般的なステータスは、コーディネーターから貴重なコンテキストを隠し、十分な情報に基づいた判断を妨げる。選択肢Cは失敗を成功としてマークすることでエラーを抑制し、いかなる回復も妨げ、不完全なリサーチ出力のリスクを負う。選択肢Dは、回復戦略が成功する可能性があるにもかかわらず、ワークフロー全体を不必要に終了させる。

#### Question 9

テスト中、統合エージェントが調査結果を組み合わせる際に、特定の主張を頻繁に検証する必要があることを観察しています。現在、検証が必要な場合、統合エージェントはコーディネーターに制御を戻し、コーディネーターがWeb検索エージェントを呼び出し、その後結果とともに統合を再度呼び出します。これによりタスクあたり2〜3回の往復が追加され、レイテンシが40%増加します。あなたの評価によると、これらの検証の85%は単純な事実確認（日付、名前、統計値）であり、15%はより深い調査を必要とします。信頼性を維持しながらオーバーヘッドを削減する最も効果的なアプローチは何ですか？

- A. 単純な照会のために統合エージェントにスコープを絞った`verify_fact`ツールを与え、複雑な検証は引き続きコーディネーター経由でWeb検索エージェントに委譲する。
- B. 統合エージェントにすべての検証ニーズを蓄積させ、パスの最後にバッチとしてコーディネーターに返させ、コーディネーターがそれらすべてを一度にWeb検索エージェントに送る。
- C. 統合エージェントにすべてのWeb検索ツールへのアクセスを与え、コーディネーター経由の往復なしにあらゆる検証ニーズを直接処理できるようにする。
- D. Web検索エージェントに、統合エージェントが検証する可能性のあるものを予測して、初期リサーチ中に各ソースの周辺の追加コンテキストを事前にキャッシュさせる。

**正解: A.** 選択肢Aは、複雑なケースのための既存の協調パターンを維持しながら、85%の一般的なケース（単純な事実検証）に必要なものだけを統合エージェントに与えることで、最小権限の原則を適用している。選択肢Bのバッチ処理アプローチは、統合のステップが以前に検証された事実に依存する場合があるため、ブロッキングの依存関係を作り出す。選択肢Cは統合エージェントに過剰にツールを提供し、関心の分離に違反する。選択肢Dは、統合エージェントが何を検証する必要があるかを確実に予測できない投機的なキャッシュに依存している。

#### Question 10

あなたのパイプラインスクリプトは`claude "Analyze this pull request for security issues"`を実行しますが、ジョブが無期限にハングします。ログは、Claude Codeが対話的な入力を待っていることを示しています。自動化されたパイプラインでClaude Codeを実行する正しいアプローチは何ですか？

- A. `-p`フラグを追加する：`claude -p "Analyze this pull request for security issues"`
- B. コマンドを実行する前に環境変数`CLAUDE_HEADLESS=true`を設定する
- C. stdinを`/dev/null`からリダイレクトする：`claude "Analyze this pull request for security issues" < /dev/null`
- D. `--batch`フラグを追加する：`claude --batch "Analyze this pull request for security issues"`

**正解: A.** `-p`（または`--print`）フラグは、Claude Codeを非対話モードで実行するための正式な方法である。プロンプトを処理し、結果をstdoutに出力し、ユーザーの入力を待たずに終了する——これはまさにCI/CDパイプラインが必要とするものである。他の選択肢は、存在しない機能（`CLAUDE_HEADLESS`環境変数、`--batch`フラグ）を参照しているか、Claude Codeのコマンド構文に適切に対応しないUnixの回避策を使用している。

#### Question 11

あなたのチームは、自動分析のAPIコストを削減したいと考えています。現在、リアルタイムのClaude呼び出しが2つのワークフローを動かしています：（1）開発者がマージする前に完了しなければならないブロッキングのマージ前チェック、（2）翌朝のレビューのために夜間に生成される技術的負債レポートです。あなたのマネージャーは、50%のコスト削減のために両方をMessage Batches APIに切り替えることを提案しています。この提案をどのように評価すべきですか？

- A. 技術的負債レポートのみにバッチ処理を使用し、マージ前チェックにはリアルタイム呼び出しを維持する。
- B. 完了を確認するステータスポーリングとともに、両方のワークフローをバッチ処理に切り替える。
- C. バッチ結果の順序の問題を避けるために、両方のワークフローでリアルタイム呼び出しを維持する。
- D. バッチが時間がかかりすぎる場合にリアルタイムにフォールバックするタイムアウトとともに、両方をバッチ処理に切り替える。

**正解: A.** Message Batches APIは50%のコスト削減を提供するが、処理時間は最大24時間で、保証されたレイテンシSLAがない。これにより、開発者が結果を待つブロッキングのマージ前チェックには不適だが、技術的負債レポートのような夜間バッチジョブには理想的である。選択肢Bは、「多くの場合より速い」完了に頼ることがブロッキングワークフローにとって受け入れられないため誤りである。選択肢Cは誤解を反映している——バッチの結果は`custom_id`フィールドを用いて関連付けることができる。選択肢Dは、各APIをその適切なユースケースに合わせるというよりシンプルな解決策があるときに、不必要な複雑さを追加している。

#### Question 12

あるプルリクエストが、株式追跡モジュール内の14個のファイルを変更します。すべてのファイルをまとめて分析する単一パスのレビューは、一貫性のない結果を生み出します：一部のファイルには詳細なフィードバックがある一方で他は表面的なコメントにとどまり、明らかなバグが見逃され、同じPR内で同一のコードをあるファイルでは問題があるとフラグを立てながら別のファイルでは承認するという矛盾したフィードバックが生じます。このレビューをどのように再構成すべきですか？

- A. 焦点を絞ったパスに分割する：各ファイルを個別にローカルな問題について分析し、その後クロスファイルのデータフローを調べる別途の統合に焦点を当てたパスを実行する。
- B. 自動レビューが実行される前に、開発者に大きなPRを3〜4ファイルのより小さな提出に分割することを要求する。
- C. すべての14ファイルに1回のパスで十分な注意を払えるように、より大きなコンテキストウィンドウを持つ上位ティアのモデルに切り替える。
- D. PR全体に対して3回の独立したレビューパスを実行し、3回のうち少なくとも2回に現れた問題のみをフラグする。

**正解: A.** レビューを焦点を絞ったパスに分割することは、根本原因——一度に多くのファイルを処理する際の注意力の希釈——に直接対処する。ファイルごとの分析は一貫した深さを保証し、別途の統合パスはクロスファイルの問題を捉える。選択肢Bは、システムを改善することなく負担を開発者に移す。選択肢Cは、より大きなコンテキストウィンドウが注意の質の問題を解決しないことを誤解している。選択肢Dは、断続的にしか捉えられない可能性のある問題に対してコンセンサスを要求することで、実際のバグの検出を実際には抑制してしまう。

## 試験の採点方法

Claude Certified Architect – Foundations試験は、規準準拠型評価（criterion-referenced assessment）です：各受験者は他の受験者と比較されるのではなく、固定されたパフォーマンス基準に照らして測定されます。ブループリントで定義された知識とスキルを示すことで合格するのであり、受験者の一定割合を上回ることで合格するのではありません。

**合格基準。** 合格スコアは、訓練を受けた専門家（subject matter experts）が最低限の適格な受験者に期待されるパフォーマンスのレベルを判断する、正式な基準設定調査（standard-setting study）を通じて設定されました。スコアは100〜1,000のスケールされた範囲で報告され、カットスコアは**720**です。スケールドスコアリングモデルは、難易度がわずかに異なる可能性のある複数の試験フォームにわたってスコアを等化するのに役立ちます。

**結果の報告。** あなたの結果は、100〜1,000のスケールドスコアとともに合格または不合格のステータスとして報告されます。あなたのスコアレポートには、各コンテンツドメイン内で正しく回答した項目の割合も表示されます。セクションレベルのパーセンテージは、あなたのパフォーマンスを理解するのに役立つよう提供されるものであり、合否の判定には使用されません。合否は、あなたの総合スケールドスコアに基づきます。

## 試験ポリシー

**本人確認。** 試験当日、有効期限内の政府発行の写真付き身分証明書を提示する必要があります。IDに記載されている名前は、登録時の名前と完全に一致していなければなりません。登録時の名前を修正する必要がある場合は、試験をスケジュールする前にcertifications-support@anthropic.comに連絡してください。

**配慮事項（Accommodations）。** 適用法に従い、証明された障害またはニーズを持つ受験者には合理的な配慮が提供されます。配慮は、試験をスケジュールする前にPearson VUEによって要求され承認されなければなりません。リクエストが承認されるまで予約をスケジュールしないでください。配慮のリクエストはpearsonvue.com/us/en/test-takers/accommodationsで行ってください。

**再受験ポリシー。** 合格しなかった受験者は、必要な待機期間の後に再受験できます。待機期間は失敗の回数ごとに増加します：1回目の失敗後**14日間**、2回目の失敗後**30日間**、3回目の失敗後**90日間**。試験は、**ローリング12ヶ月の期間内で最大4回**まで受験できます。制限は各試験ごとに適用されるため、ある試験に合格しなかったことが、別の試験への登録を妨げることはありません。受験料は各回の受験ごとに適用されます。

**無断欠席と遅刻。** スケジュールされた試験に現れなかった受験者、または許可された遅刻の猶予時間を過ぎて到着した受験者は、受験料を没収され、再登録しなければなりません。キャンセルと再スケジュールの締め切りについては、上記の「登録とスケジューリング」に記載されています。

## 試験当日の体験と行動規範

試験は、標準化された安全な監督付き環境で実施されます。オンラインで受験する場合でもPearson VUEテストセンターで受験する場合でも、この資格を保持するすべての人のためにその信頼性を保護するため、以下のルールが適用されます。

試験中、あなたは以下を守らなければなりません：

- オンラインで受験する場合、セッション全体を通じて監督者とウェブカメラの視野内にとどまること
- 作業スペースをメモ、書籍、電話、セカンドモニター、その他の資料がない状態に保つこと
- 試験中に他の人とコミュニケーションを取らないこと
- いかなる形式でも試験内容をキャプチャ、コピー、撮影、または複製しないこと

禁止されている物品には、携帯電話、スマートウォッチ、ヘッドフォン、学習資料、および録音デバイスが含まれます。もし許可される物品があるとすれば、監督者から提供されるスクラッチペーパーのようなものであり、Pearson VUEによって指定されます。

**不正行為の結果。** カンニング、禁止されたリソースへのアクセスの試み、または試験内容の開示は、結果の無効化、資格の取り消し、将来の試験受験の禁止につながる可能性があります。

## 資格の維持と再認定

Claude Certified Architect – Foundations資格は、授与された日から**12ヶ月間**有効です。基盤となる技術が急速に進化するため、資格保有者が最新の知識を維持できるよう、この資格は期限付きとなっています。

試験内容が大幅に変更された場合、Anthropicは資格保有者に対し、更新アセスメントを完了するのではなく、試験全体を再受験して再認定することを要求する場合があります。

- **確信度スコアリング** — フィールドレベルの確信度、ラベル付き検証セットによる較正、誤り率測定のための層化サンプリング
